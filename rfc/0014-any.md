# RFC 0014: `dyn Any` — Explicit Erasure with Checked Recovery

- **Status:** Draft
- **Date:** 2026-08-22
- **Author:** hpp2334
- **Depends on:** RFC 0005 (builtin generics — `Option`), RFC 0012
  (interfaces & `dyn` — read §2 after), RFC 0015 (reification — read §1 after)
- **Supersedes:** RFC 0002 §3.1 (pre-restructure)
- **Part:** B — Language surface

## Summary

`Any` is the **universal builtin interface** and `dyn Any` its object type:
a heap cell that **forgets the static type and keeps the runtime type** —
the controlled replacement for `any`, built on reification (RFC 0015).
Erasure is a *named function you call*; the static type system never
loosens, and rut keeps **no cast syntax at all** (`as` is reserved and
always errors, RFC 0002 §4).

- `make_any(v): dyn Any` — a prelude builtin provided by the host, box any
  value. `Any` rides the ordinary interface machinery: every type
  implicitly implements it, nobody may declare or list it (`implements Any`
  and `T: Any` bounds are compile errors — vacuous). **Value semantics
  apply at boxing time**: a dataclass or bare class value is snapshotted
  (copied into the cell); ref values (`Array`, `string`, `Rc<T>`) store the
  handle. To share a class by identity, box the handle:
  `make_any(Rc(c))`.
- `downcast<T>(a: dyn Any): Option<T>` — checked recovery. `T` must be
  **concrete** — an interface type argument (any `dyn I`, including
  `dyn Any` itself) is a compile error (RFC 0012 §3); interface values
  have no recovery path by design. `None` on
  mismatch — never a trap.
- `is<T>(a)` sees through the box (the boxed value's type), same
  concrete-`T`-only rule.
- **That is the whole API** — apart from the three layout accessors of
  RFC 0015 §3 (`type_id()`, `size()`, `as_bytes()`, callable on `dyn Any`):
  no methods, no fields, no equality (OQ-1), no `f""` formatting. A
  `dyn Any` can't do anything until it is recovered — which is exactly how
  it differs from gradual typing.
- Crossing isolates: allowed iff the boxed value's type is crossable
  (RFC 0021 §3), checked at runtime via the type descriptor.
- Also the host-FFI escape hatch for host data with no static shape
  (RFC 0023).

Because `Any` is an interface, `dyn Any` composes in every type position:
`Rc<dyn Any>`, `Array<dyn Any>`, fields, returns — it is the **bottom of
the interface tier** in the type lattice: `exact concrete > dyn I > dyn
Any` (RFC 0031 §4). The old `Opaque` builtin is gone; nothing about it
remains on the language surface.

## IR contract (why `dyn Any` does not break optimization)

1. **Boxes are immutable.** `make_any(v)` snapshots its value; no
   operation mutates a box in place (store-style writers swap whole cells).
2. **`downcast` is therefore pure** in `(cell, T)`: the compiler may CSE
   repeated downcasts of the same cell, hoist invariant checks out of
   loops, and cache results — validity is permanent.
3. **`downcast` is a refinement point**: within the `is_some()` branch the
   value's lattice position is *exact concrete type* — everything
   downstream optimizes as if the value had never been erased.
4. **Downcast chains over one cell fold to a `TypeId` switch** (jump
   table), the erasure analogue of exhaustive `when`.
5. **`dyn Any` is a storage type, not a flow type**: lints flag
   downcasts inside loop bodies and `dyn Any` parameters/returns on
   non-storage functions. The hot path keeps concrete types.

The lattice machinery itself is RFC 0031 §4. See
**`examples/basic/any.rut`**. The motivating user-land pattern — a
tur-style reactive store (`state` / `source` / `derive` / `mutation` /
`watch` / `Store`, with an `Atom` interface unifying the three atom kinds
for `watch`) — is **`examples/gui/dashboard/reactive.rut`**; the app-shaped
consumer is the `examples/gui/dashboard/` project (`state.rut` declares the
graph, `main.rut` runs it end to end).

## Open questions

- OQ-1: `Any` extras: the `type_id()` accessor **shipped** (RFC 0015 §3,
  with `size()` and `as_bytes()`); content equality/hashing for identity use in
  collections remains open — `std:collection`'s `Equal<T>` / `Hashable`
  interfaces (RFC 0026, RFC 0028) are the shipped answer for user types.
- OQ-2: derived-atom caching (deps/version tracking for `derive`-style
  user libraries) — pure recompute-on-read is the v1-simple contract;
  decide whether the stdlib ships an invalidation-based cache.
