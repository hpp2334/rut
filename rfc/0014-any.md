# RFC 0014: `Opaque` — Explicit Erasure with Checked Recovery

- **Status:** Draft
- **Date:** 2026-08-23
- **Author:** hpp2334
- **Depends on:** RFC 0005 (builtin generics — `Option`), RFC 0012
  (traits & `dyn` — read §2 after), RFC 0015 (reification — read §1 after),
  RFC 0025 (host fns & declaration files)
- **Supersedes:** RFC 0002 §3.1 (pre-restructure)
- **Part:** B — Language surface

## Summary

`Opaque` is the **erasure-box engine builtin**: a concrete type whose
values box any value — **forgetting the static type and keeping the
runtime type** — the controlled replacement for `any`, built on
reification (RFC 0015). Erasure is a *method call you write*; the static
type system never loosens, and rut keeps **no cast syntax at all**
(`as` is reserved and always errors, RFC 0002 §4).

- `pub builtin Opaque` — declared in `std:core`'s declaration file
  (RFC 0025, revised — the engine's own contract, like `Option`/
  `Result`) and backed by the same `RutOpaque` cell kind the VM
  already uses for host opaques (RFC 0016 §5). Construction **is**
  erasure —
  `Opaque.new(v)`, the builtin's class method (RFC 0010 §1):
  **`Opaque.new(v) -> Opaque`** — every value can become `Opaque`, and since
  every non-primitive is already a shared cell (RFC 0016 §1), the box
  **stores the handle: zero-copy, identity-preserving** — mutations
  through the original name are visible through the box. `Opaque.new(x) ==
  Opaque.new(x)` is `false` (two boxes, RFC 0012 §4) — box once, compare
  boxes.
- `downcast<T>(o: Opaque) -> Option<T>` — checked recovery. `T` must be
  **concrete** — a trait-object type argument (any `dyn I`) is a compile
  error (RFC 0012 §3); trait objects
  have no recovery path by design. `None` on
  mismatch — never a trap.
- **Host payload boxes** (RFC 0023/0026): the embedder can news the box
  itself — `OpaqueBox::alloc(vm, any_rust_value)` — behind the same
  `Opaque` surface. The payload is Rust, so rut sees only the box:
  `o is Opaque` is `true`, `o is T` misses for every rut `T`, and
  `downcast<T>` is `None` for every `T` (the box's runtime type is a
  reserved host sentinel no table index can equal — the miss is checked,
  never a trap). The host borrows the payload back typed
  (`with`/`with_mut`, call-scoped, borrow-guarded per RFC 0023 §2); the
  payload's Rust `Drop` runs when the box's rc hits 0 (RFC 0016 §3).
- `o is T` / `o is I` **see through the box** (the boxed value's type):
  concrete `T` is the exact-type test, a trait RHS is the
  capability probe — does the boxed value's exact type have an impl for
  `I`
  (RFC 0012 §3, RFC 0015 §6). `x is Opaque` (on a non-box receiver) is
  the ordinary concrete test for the box type itself.
- **That is the whole API** — apart from the three layout accessors of
  RFC 0015 §3 (`type_id()`, `size()`, `as_bytes() -> bytes`): no
  methods, no fields, no `f""` formatting. An
  `Opaque` can't do anything until it is recovered — which is exactly how
  it differs from gradual typing.
- Crossing isolates: allowed iff the boxed value's type is crossable
  (RFC 0021 §3), checked at runtime via the type descriptor.
- Also the host-FFI escape hatch for host data with no static shape
  (RFC 0023).

`Opaque` is a **concrete class, not a lattice node**: it composes in
every type position trivially (`Vec<Opaque>`,
`Array<Opaque, 3>`, fields, returns) because it is just a type — there
is no widening to it (the trait tier is `exact concrete > dyn I`,
RFC 0031 §4). `dyn
Slice<T>` is **not boxable** (`Opaque.new(..)` rejects slices — as it
rejects any `dyn`-typed value — while fixed `Array<T, N>` boxes fine:
it is concrete, and its TypeId covers `T` and `N`). Slices are never
boxed, period.

## IR contract (why `Opaque` does not break optimization)

1. **Boxes are never re-sealed.** The `Opaque.new(v)` cell is written once
   at construction; store-style writers swap whole cells, never retype
   one.
2. **`downcast` is therefore pure** in `(cell, T)`: the compiler may CSE
   repeated downcasts of the same cell, hoist invariant checks out of
   loops, and cache results — validity is permanent.
3. **`downcast` is a refinement point**: within the `is_some()` branch the
   value's lattice position is *exact concrete type* — everything
   downstream optimizes as if the value had never been erased.
4. **Downcast chains over one cell fold to a `TypeId` switch** (jump
   table), the erasure analogue of exhaustive `when`.
5. **`Opaque` is a storage type, not a flow type**: lints flag
   downcasts inside loop bodies and `Opaque` parameters/returns on
   non-storage functions. The hot path keeps concrete types.

Mechanically none of this is op magic (RFC 0032 §1.1): `downcast<T>` is
a generic **prelude function** over the type machine's two primitives —
`tidof` (read the cell's runtime `TypeId`), `icmp`, `br`, a guarded
`unbox`, `optsome`/`optnone` on the arms; `Opaque.new(v)` is its mirror, an
internal-native call (RFC 0022 §2). Both names are imported from
`"std:core"` (RFC 0028). The check being visible dataflow is
what makes 2 and 4 ordinary optimizations over a pure load — an opaque
`downc` op would block both.

The lattice machinery itself is RFC 0031 §4. See
**`examples/basic/opaque.rut`**. The motivating user-land pattern — a
tur-style reactive store (`state` / `source` / `derive` / `mutation` /
`watch` / `Store`, with an `Atom` trait unifying the three atom kinds
for `watch`) — is **`examples/gui/dashboard/reactive.rut`**; the app-shaped
consumer is the `examples/gui/dashboard/` project (`state.rut` declares the
graph, `main.rut` runs it end to end).

## Open questions

- OQ-1: `Opaque` extras: content equality/hashing for identity use in
  collections — `std:collection`'s
  `Hashable` trait (RFC 0026, RFC 0028) covers user types; decide
  whether `Opaque` itself needs more. (The layout accessors
  `type_id()`/`size()`/`as_bytes()` are normative in §1 and
  RFC 0015 §3.)
- OQ-2: derived-atom caching (deps/version tracking for `derive`-style
  user libraries) — pure recompute-on-read is the v1-simple contract;
  decide whether the stdlib ships an invalidation-based cache.
